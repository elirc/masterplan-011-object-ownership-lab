## Follow one path, not every file

Start at [public/core.js](../public/core.js) and locate `Widget.prototype.describe`. Use this trace as a map: new Widget("Map") creates A with an own name → lookup of A.describe finds no own property → lookup continues on Widget.prototype → the call uses A as its receiver → the result includes Map. Assigning A.describe changes the first lookup step; B still follows the original route.

The tooling is intentionally separate from the product concept. You can study the local server or CI after the main rule is clear. Neither an HTTP preview server nor a workflow configuration should become a prerequisite for understanding an inline-block box or a small pure function.

## Decision: Share behavior, keep values per instance

Placing name on each new object gives each widget independent data. Sharing a method on the prototype avoids confusing behavior ownership with data ownership. The reference does not modify Object.prototype, and the shared function reads the receiver supplied by the call. Compare two function identities as well as two return values: identical output alone would not prove the function is shared.

**Review question:** What changes if you allocate a new function inside every constructor call?

**Your alternative:** Write a plausible different choice, then give a concrete example that reveals its cost. “More scalable” or “cleaner” is not enough; identify a changed dependency, a new state to manage, or a user-visible failure mode.

## Decision: Show shadowing with an own property

The shadow button assigns a method on A. It leaves the prototype untouched, which is why B continues to describe itself normally. The restore button deletes that single own property. This is an explicit lookup exercise, not a mechanism for patching global language behavior.

**Review question:** Why does assigning undefined fail to restore the inherited method?

**Your alternative:** Write a plausible different choice, then give a concrete example that reveals its cost. “More scalable” or “cleaner” is not enough; identify a changed dependency, a new state to manage, or a user-visible failure mode.

## Decision: Fail visibly on a lost receiver

The prototype method checks that its receiver is a Widget. A detached call therefore produces an intentional diagnostic instead of an obscure property-read failure. Calling the same function with .call(a) supplies the missing receiver without creating another widget.

**Review question:** Which expression supplies this in a.describe(), and what supplies it in method.call(a)?

## Change boundaries

A small change should begin in the file that owns its meaning. Change domain rules in the core, wording and interaction in the browser adapter, and layout in the relevant CSS rule. For the static references, semantic information belongs in HTML before styling. For the Git reference, the staged snapshot boundary belongs in the helper rather than being guessed from editor state.

If a story crosses two files, say why. A new unit, weather option or UI station may require a contract, a control and tests to change together. That is a coherent feature boundary, not permission to rewrite unrelated parts of the project.

## Deliberate limits

Persistence and frameworks are explicit where used: M019 saves a namespaced local draft; M024–M025 introduce React. The remaining builds use plain JavaScript and local data. M025 saved definitions last for the current session only. The preview server is a local development aid, not a production hosting system. A browser screenshot is one observation, not proof of every device or assistive technology. Keep these limits visible when describing your own work.
